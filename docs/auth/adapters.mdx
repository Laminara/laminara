Laminara не хранит аккаунты. Логины и пароли остаются там, где они у вас уже есть — в базе сайта, в отдельном файле или за вашим API. Laminara обращается к этому источнику через **адаптер**, проверяет пару логин/пароль и владеет только сессиями.

Раздел `auth` состоит из трёх частей: провайдер (откуда аккаунты), хеш пароля и хранилище сессий.

## Провайдеры

<Tabs>
  <TabItem label="jsonfile">
    Аккаунты в JSON-файле. Годится для небольшого списка или на старте.
    ```json
    {
      "provider": "jsonfile",
      "config": {
        "path": "/var/lib/laminara/users.json",
        "hash": "argon2id",
        "fields": { "username": "username", "password": "password", "uuid": "uuid" }
      },
      "sessions": { "backend": "memory" }
    }
    ```
    Сам файл — массив объектов; `fields` задаёт, какие ключи считать логином, паролем и (необязательно) UUID.
  </TabItem>
  <TabItem label="sql">
    Аккаунты в вашей базе — Postgres или MySQL. Laminara только читает.
    ```json
    {
      "provider": "sql",
      "config": {
        "driver": "postgres",
        "dsn": "postgres://ro:pass@db:5432/site?sslmode=require",
        "table": "users",
        "hash": "bcrypt",
        "fields": { "username": "nickname", "password": "password_hash", "uuid": "uuid" }
      },
      "sessions": { "backend": "redis", "redisAddr": "redis:6379" }
    }
    ```
    По этому соединению ходят хеши паролей, поэтому база за пределами машины требует TLS: `sslmode=require` у Postgres, `tls=true` у MySQL и MariaDB. Отключать шифрование можно, только когда база на том же хосте.

    `fields` сопоставляет логические поля с колонками вашей таблицы — подстраивать чужую схему под Laminara не нужно. Имена таблицы и колонок проверяются, произвольный SQL в них не подставить.

    **Если одной таблицей не обойтись** — пароли лежат отдельно, есть флаг бана, нужен вид — задайте запрос сами вместо `table` и `fields`:

    ```json
    {
      "provider": "sql",
      "config": {
        "driver": "mariadb",
        "dsn": "laminara:pass@tcp(127.0.0.1:3306)/site?charset=utf8mb4&tls=true",
        "hash": "argon2id",
        "query": "SELECT p.hash, u.uuid FROM users u JOIN user_passwords p ON p.user_id = u.id WHERE u.username = ? AND u.is_banned = 0"
      }
    }
    ```

    Запрос принимает логин единственным подстановочным знаком (`?` для MySQL и MariaDB, `$1` для Postgres) и выбирает **сначала пароль, затем при желании UUID**. Ничего кроме этих двух колонок возвращать не нужно.

    Так же решается и бан: условие живёт в вашей схеме, и только ваш запрос может его учесть. Игрок, помеченный забаненным на сайте, просто не найдётся — и не войдёт.
  </TabItem>
  <TabItem label="http">
    Проверку логина делает ваш сервис — Laminara шлёт ему запрос.
    ```json
    {
      "provider": "http",
      "config": {
        "url": "https://site.example/api/auth",
        "usernameField": "login",
        "passwordField": "password",
        "uuidField": "uuid",
        "successField": "ok"
      },
      "sessions": { "backend": "redis", "redisAddr": "redis:6379" }
    }
    ```
    Laminara кладёт логин и пароль в указанные поля запроса, считает вход успешным по полю `successField` в ответе и берёт оттуда же UUID.
  </TabItem>
</Tabs>

## Хеш пароля

Поле `hash` (у jsonfile и sql) говорит, как пароль захеширован в вашем источнике. Laminara хеширует введённый пароль тем же способом и сравнивает. Доступны:

`argon2id` · `bcrypt` · `sha256` · `sha512` · `md5` · `plain`

Без этого поля берётся `argon2id`. Схему указывают под свою базу: если она не совпадёт с настоящей, вход не пройдёт ни у кого и сервер скажет, что хранимый пароль не читается.

<Aside type="caution">
`sha256`, `sha512`, `md5` и `plain` оставлены только ради совместимости со старыми базами: соли в них нет, и утёкшая база перебирается на видеокарте. При старте с такой схемой сервер пишет предупреждение в лог — оно снимается переводом базы на `argon2id` или `bcrypt`.
</Aside>

## Двухфакторная аутентификация

Второй фактор — одноразовый код из приложения-аутентификатора (TOTP): подойдёт Google Authenticator, Яндекс.Ключ и любое совместимое приложение. Включается на игрока, а не на весь проект: у кого секрет есть, тот входит по паролю и коду, у кого нет — как раньше.

Секрет выпускает консоль:

```
auth totp <игрок>
```

Команда печатает base32-секрет и строку `otpauth://` — приложение-аутентификатор подхватит из неё коды. Секрет впишите игроку в источник аккаунтов (как именно — зависит от провайдера, см. ниже), и вход без кода закроется; sql подхватывает секрет сразу, jsonfile — после перезапуска проекта. Отключить двухфакторку так же просто: уберите секрет. Игрок потерял телефон — выпустите новый секрет и попросите добавить его заново.

<Tabs>
  <TabItem label="jsonfile">
    Ключ записи, по умолчанию `totp` (меняется полем `fields.twoFactorSecret`):

    ```json
    { "username": "neo", "password": "…", "totp": "JBSWY3DPEHPK3PXP" }
    ```
  </TabItem>
  <TabItem label="sql">
    Колонка таблицы, задайте её полем `fields.twoFactorSecret`:

    ```json
    "fields": { "username": "login", "password": "password_hash", "twoFactorSecret": "totp_secret" }
    ```

    Пустая колонка — у игрока двухфакторки нет. Со своим запросом (`query`) второй фактор не работает: колонку в ответе неоткуда взять.
  </TabItem>
  <TabItem label="http">
    Код уходит вашему сайту вместе с логином и паролем — проверяете его вы. Поле кода в запросе задаёт `codeField` (по умолчанию `totp`); сам код подставляется, только когда игрок его ввёл.

    Когда ваш сайт отвечает отказом и поднимает поле `secondFactorField`, лаунчер показывает поле для кода, а не «неверный пароль»:

    ```json
    "secondFactorField": "needTotp"
    ```
  </TabItem>
</Tabs>

Код меняется каждые 30 секунд; принимается код текущего и соседних интервалов, чтобы часы не обязаны совпадать до секунды. Один и тот же код принимается дважды — лаунчер проверяет его в двух шагах входа; третий раз не пройдёт.

<Aside type="caution">
Игрок с включённой двухфакторкой входит только через ваш лаунчер. Сторонние лаунчеры (через authlib-injector) передать код не могут — вход для них закроется с сообщением о необходимости кода.
</Aside>

## Сессии

Пароль проверяется один раз; дальше клиент живёт по токенам, которые выдаёт и хранит Laminara. Токен доступа короткий, токен обновления — длинный. При обновлении старый токен отзывается, а попытка воспользоваться отозванным распознаётся.

- `backend: "memory"` — сессии в памяти процесса. Просто, но не переживают перезапуск и не годятся для нескольких экземпляров.
- `backend: "redis"` с `redisAddr` — сессии в Redis: переживают перезапуск и общие для нескольких экземпляров сервера.

Сроки жизни токенов задаются полями `accessTTL` и `refreshTTL` рядом с `provider` (например, `"15m"` и `"720h"`).

<Aside type="note">
Тот же источник аккаунтов обслуживает и вход в игре — см. [Вход в игре и скины](/auth/yggdrasil). Настраивать его дважды не нужно.
</Aside>
