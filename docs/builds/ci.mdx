Версионированный JSON описывает одну сборку. Имена файлов в `path` — пути внутри сборки,
`source` — локальные файлы относительно описания. Ссылки за пределы каталога описания
не принимаются. Служебные каталоги runtime, assets, libraries, versions и platforms
заполняет install; загрузка поверх них запрещена.

```json
{
  "version": 1,
  "name": "survival",
  "minecraft": "1.21.1",
  "loader": "vanilla",
  "compat": "off",
  "platforms": ["windows-x64", "linux"],
  "sourceRevision": "git-commit-or-release-name",
  "settings": {
    "serverAddress": "play.example.com:25565",
    "enforced": ["mods/"]
  },
  "files": [
    {"path": "mods/example.jar", "source": "files/example.jar", "sha256": "", "size": 0}
  ]
}
```

Для модового загрузчика нужны `loader` и точная `loaderVersion`. Рецепт совместимости
задаётся как `compat: "имя:версия"`; `latest` и незакреплённый рецепт отвергаются.
Minecraft также задаётся точной версией. Поле `java` при необходимости выбирает компонент
Mojang. Необязательное поле `runtimeVersions`, например `{"linux":"21.0.7"}`, задаёт
ожидаемое имя версии Java для каждой платформы. Если Mojang предлагает другую версию,
apply завершится ошибкой и сохранит прежнюю публикацию; исторический runtime автоматически
не разыскивается. Без этого поля runtime выбирается при install. Версия authlib-injector
пока не закрепляется описанием, поэтому JSON фиксирует не все версии сторонних
артефактов. Опубликованные файлы сохраняются в CAS; rollback восстанавливает именно их.

CLI вычисляет SHA-256 и размер каждого source. Если `sha256` задан, несовпадение останавливает
работу до загрузки. `validate` возвращает описание с вычисленными хешами, без локальных путей.
Лимиты первой версии: 48 КиБ JSON, до 200 файлов, 512 МиБ на файл и 8 ГиБ на сборку.

```sh
laminara-server build validate pack.json
laminara-server build plan pack.json > plan.json
laminara-server build push pack.json
laminara-server build apply pack.json --revision "$(jq -r .revision plan.json)" \
  --key pipeline-42 --json
laminara-server builds --json
```

`plan` возвращает текущую ревизию, `inputDigest`, `noOp` и недостающие хеши. Он не сохраняет
описание и не скачивает игровые файлы. `push` загружает только отсутствующие объекты
частями до 1 МиБ; повтор продолжает незавершённую загрузку. При окончании сервер проверяет
размер и SHA-256. Кэш ограничен 16 ГиБ; загрузки старше суток удаляются при следующей загрузке.

`apply` включает push, затем запускает задание. Оно готовит все платформы в отдельном
каталоге, проверяет пользовательские настройки, публикует объекты и одним переключением
указателя делает новую публикацию доступной игрокам. При ошибке остаётся прежняя публикация.
Изменение сборки после plan даёт конфликт. Параллельные операции одной сборки отклоняются;
после завершения первой получите новый план. Повтор уже применённого состояния возвращает
`noOp`, не выполняя install или publish. После завершения CLI проверяет это состояние ещё раз.

`sourceRevision` хранится отдельно от версии формата и текущего поля version манифеста.
`builds --json` возвращает её вместе с `inputDigest`, `releaseId` и `retainedReleases`.
Для применения без ожидания добавьте `--detach`, затем используйте `jobs watch ID`.

## Откат

```sh
laminara-server builds --json
laminara-server exec build-rollback survival PREVIOUS_RELEASE_ID
```

Восстанавливается целая сохранённая публикация со всеми платформами. История поколений
и CAS-объекты сохраняются для старых лаунчеров. Автоматического удаления поколений пока нет.
После CI-применения рабочий каталог находится внутри
`profiles/NAME/.laminara/workspaces/ID`; TUI и серверные команды находят его по указателю.
Ручное изменение файлов старой рабочей копии не меняет уже подписанные манифесты.
Посторонние сборки apply никогда не удаляет; удаление выполняется явно командой `delete`.
При первой публикации новым сервером прежние манифесты старого формата сохраняются
в истории вместе с метаданными отката. После этого к прежней публикации можно вернуться
через `build-rollback`, выбрав её ID из `retainedReleases`.

## GitHub Actions

Пример ручного workflow — `.github/workflows/build-apply.yml`. Он требует variables
`LAMINARA_CLI_IMAGE` (образ CLI, желательно по digest), `LAMINARA_ADMIN_URL` и secret
`LAMINARA_ADMIN_TOKEN` с правами `read,builds`. Настройте доступ runner к административной
сети. Workflow проверяет описание, получает plan, загружает файлы и ждёт apply.
Сам по себе push репозитория не запускает публикацию сборки.
