Модули

Модуль — это исполняемый файл, который сервер запускает отдельным процессом и с которым общается по gRPC. Модуль добавляет команды в единый реестр сервера, поэтому его команды появляются в CLI, консоли, exec и help наравне со встроенными; он же может подписаться на события и отдать серверу свои провайдеры — аутентификации, скинов, доступа к сборкам и новостей. Падение модуля не роняет сервер, а писать модуль можно на любом языке, поддерживающем gRPC-контракт (Go — из коробки, через SDK).

Настройка через TUI

На главном экране консоли нажмите m. Тот же список находится в Настройки проекта → Модули → Настройки модулей. Он объединяет установленные исполняемые файлы и сохранённые настройки. Создавать блок в JSON вручную не нужно. Положите модуль в папку modules.dir и перезапустите сервер: список обновляется при запуске.

У каждого установленного модуля показано, загрузился ли он и доступны ли отдельные поля. Модуль, которому не хватает обязательных параметров, остаётся в списке: откройте его, заполните поля и нажмите s. Консоль покажет изменения и ошибки до записи. После сохранения нужен перезапуск сервера (r); горячее применение настроек не поддерживается. x на поле удаляет сохранённое значение, возвращая объявленный default, если он есть. Поиск в общих настройках находит и поля модулей.

На снимках показан проверочный модуль с разными типами полей. У каждого модуля свой набор настроек.

Проверка значения происходит при вводе. При ошибке текст остаётся в редакторе, чтобы его можно было исправить. Esc отменяет ввод вместе с сообщением об ошибке.

В списке модулей действие «настроить по имени файла» создаёт только конфигурацию. Сам файл модуля устанавливается отдельно. x сбрасывает настройки выбранного модуля после подтверждения; исполняемый файл остаётся на месте.

Настройки остаются в основном config.json:

Ключ записи совпадает с именем исполняемого файла, а не с названием из Info. Имя файла стабильно связывает сохранённые параметры с модулем; переименование файла требует переноса соответствующего блока. Точки и пробелы в именах поддерживаются. В технических путях Admin API точка внутри имени кодируется как %2E, процент как %25: modules.config.my%2Eplugin.greeting. В самом JSON имя остаётся my.plugin.

Сохраняются только явно заданные значения. Изменение отдельного поля не удаляет неизвестные модулю или новой схеме ключи. Секреты скрыты в ответах API и при просмотре изменений; в конфиге они хранятся обычным текстом. Для внешнего хранения используйте ${env:NAME} или ${file:path}. В режиме external доступны просмотр, подготовка правок и экспорт; запись выполняется через внешний источник конфигурации.

Описание полей в SDK

Реализуйте module.SettingsDescriber: метод Settings() module.SettingsDescriptor. Описание не зависит от состояния терминала и подходит другим клиентам Admin API.

Рабочий пример находится в examples/modules/greeter/main.go в исходниках. SDK отправляет такое описание с version: 1. Сервер проверяет поля и подставляет отсутствующие defaults перед Configure; в файл эти значения автоматически не записываются. Явные false, 0 и пустые списки остаются явными значениями. После очистки поля следующий запуск использует default из установленной версии модуля.

Словари и списки открываются отдельным экраном. После изменения элемента курсор остаётся на нём; после добавления выбирается новая запись. Esc возвращает к исходному полю формы. Длинные списки вариантов выбора прокручиваются внутри меню.

Для секретов используйте secret или secret-json; обычные text, map и json считаются открытыми данными. Секретный default в схеме запрещён.

key задаёт путь внутри настроек модуля: connection.timeout создаёт вложенный объект. label и hint описывают поле, group объединяет соседние поля под заголовком. required запрещает пустое строковое значение и null; отсутствующее поле допустимо, если у него есть default. options обязателен для choice. Для целых чисел min и max включают границу; в Go это указатели *int64, поэтому нулевая граница отличается от отсутствующей. Default передаётся строкой: "true", "3", "10s", для списка или словаря строка содержит JSON.

Схема ограничена 64 КиБ и 128 полями на модуль или провайдер. Пересекающиеся пути (server и server.token), неизвестные типы, неподдерживаемые версии и неверные defaults отклоняются. В этом случае сервер пишет причину в журнал, а TUI оставляет скрытый JSON для ручной настройки. Сервер проверяет значения при сохранении и загрузке; проверки соединений и предметных правил остаются в Configure.

Как устроен контракт

Поток загрузки: DescribeSettings → проверка схемы и параметров → Configure → Info. DescribeSettings возвращает метаданные и схему без регистрации команд и событий. Поэтому Info(), Settings() и методы перечисления провайдеров должны работать до Configure и не открывать соединения. Команды и обработчики становятся доступны только после успешного Configure.

Если конфигурация отклонена, процесс останавливается, но описание остаётся в памяти сервера до его перезапуска и доступно редактору. Незаданный блок нового модуля не блокирует сохранение остальных настроек сервера. Уже созданный блок проверяется целиком: обязательные поля можно заполнить одним набором правок и сохранить вместе. Если не настроенный модуль выбран основным провайдером, например auth.provider, сервер по-прежнему не запускается без рабочего провайдера. Сначала настройте модуль, затем выбирайте его в качестве обязательного источника.

TUI получает поля через существующие ListSettings и PreviewSettings; изменения отправляет через ApplySettings. В SettingEntry передаются тип, варианты, default, группа, обязательность и числовые границы. Другой интерфейс использует тот же API, проверку ревизии и серверный валидатор. Свой путь записи или запуск модулей UI не нужен.

Старый SettingsSchemaJSON() []byte остаётся доступен для совместимости и других языков. Его формат такой же: module содержит массив полей, providers содержит схемы адаптеров. Без version сохраняется прежняя семантика: defaults показывает редактор, а применяет сам модуль. Для версии 1 defaults настроек модуля применяет сервер. Старые бинарники без RPC DescribeSettings загружаются прежним порядком Configure → Info; для настройки до первого успешного запуска пересоберите модуль с новым SDK.

Настройки провайдеров

Объект providers описывает конфигурацию объявленных модулем провайдеров по ключам auth/имя, skin/имя, access/имя, news/имя:

Эти поля находятся в настройках соответствующего адаптера (auth.config и другие), а не в modules.config. Defaults провайдера применяет его фабрика OpenAuth, OpenSkin и т. п. Поле providers не регистрирует новый провайдер само по себе: имя должно быть объявлено соответствующим интерфейсом модуля.

Секреты в командах

По умолчанию аргументы команды модуля скрыты из истории и эха TUI. Если они заведомо не содержат секретов, установите SafeArguments: true в module.Command. Для команды, возвращающей пароль или токен, установите SecretOutput: true: её вывод получит только вызывающий клиент, без общего журнала. Такие команды выполняются напрямую и не сохраняются в истории фоновых заданий. Разрыв соединения с ними не поддерживает продолжение; остальные команды могут выполняться через jobs.

Провайдеры

Модуль может отдать серверу провайдер — реализацию одного из адаптеров, которые сервер выбирает по имени в конфиге. Провайдер модуля встаёт в тот же реестр, что и встроенные, поэтому в конфиге он пишется ровно так же, как jsonfile или http:

ВидИнтерфейс модуляГде называется в конфиге
АутентификацияAuthProviders + AuthProviderauth.provider
СкиныSkinProviders + SkinProvideryggdrasil.skinProvider
Доступ к сборкамAccessSources + AccessSourceaccess.sources.<имя>.type
НовостиNewsSources + NewsSourcenews.source.type

Первый интерфейс перечисляет имена, второй — работает. Сервер запрашивает список при загрузке модуля, а открывает провайдер тогда, когда доходит до него в конфиге, и передаёт соседний блок настроек: для аутентификации это auth.config, для скинов yggdrasil.skinConfig, для доступа и новостей — config рядом с type.

Две ошибки из SDK — ErrInvalidCredentials и ErrTwoFactorRequired — сервер понимает как отдельные исходы: первая приводит к отказу и тратит бюджет попыток, вторая просит лаунчер показать поле для кода из приложения-аутентификатора. Любая другая ошибка считается сбоем модуля, а не неверным паролем. UUID — строка в обычном формате; если модуль оставит её пустой, сервер посчитает офлайновый UUID от ника.

Имя провайдера должно быть свободным: занятое встроенным адаптером или другим модулем имя сервер не примет и напишет об этом в журнал, а не подменит существующий провайдер молча. Модули загружаются раньше, чем сервер читает конфиг, поэтому провайдер модуля доступен уже при первом запуске — и виден в списке вариантов на экране настроек.

Модуль не поднялся

Сервер пишет причину в журнал и повторяет её в laminara-server doctor --only modules.

«модулю негде создать свой сокет: временный каталог … только для чтения». Модуль — отдельная программа, и говорит она с сервером через unix-сокет во временном каталоге. Если unit systemd написан с ProtectSystem=strict, но без PrivateTmp=true, /tmp доступен только для чтения. Сам сервер в таком случае заводит tmp/ рядом со своими данными и модули поднимаются как обычно — эта ошибка означает, что запасной каталог тоже не получился. Перепишите unit тем, что печатает сам сервер:

«модуль пропущен: файл не исполняемый». chmod +x на файл модуля.

«модуль не поздоровался с сервером». Файл не модуль Laminara, собран под другую версию SDK или падает при старте. Запустите его руками — модуль ответит This binary is a plugin. These are not meant to be executed directly.; всё остальное на выходе и есть причина.

Владелец файла модуля роли не играет: сервер запускает его от своего пользователя, и достаточно права на чтение и запуск. Строки Owner: и Group: в журнале — справка go-plugin, а не диагноз.

Чем модуль может распоряжаться

Каталог модулей — то же доверие, что и сам бинарь сервера. Сервер запускает оттуда любой исполняемый файл от своего пользователя: модуль читает те же файлы, ходит в ту же базу и в ту же сеть. Изоляции нет — отдельный процесс нужен, чтобы падение модуля не роняло сервер, а не чтобы ограничить его в правах.

Отсюда два правила:

  • каталог принадлежит пользователю сервера и никому больше не пишется (chown laminara: /var/lib/laminara/modules && chmod 750 …). Кто может положить туда файл — тот выполняет код на вашем сервере;
  • чужой модуль ставится так же, как любая программа на сервер: по исходникам, которые вы можете прочитать, из релиза, за который отвечает известный вам автор.

Провайдер аутентификации из модуля вдобавок решает, кого пускать: он видит логин и пароль игрока в открытом виде и сам выносит вердикт. Это неизбежно для внешней CMS — но модуль, который так делает, стоит выбирать особенно придирчиво.
